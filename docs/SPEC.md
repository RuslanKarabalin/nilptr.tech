# SPEC

## Функционал

### Публичная часть

- лента опубликованных постов и страница поста
- отдельные страницы (например CV), на которые можно сослаться из хедера
  или футера
- хедер и футер с кнопками и ссылками, редактируемые из админки
- кнопка смены темы (тёмная, светлая), выбор сохраняется в браузере
- кнопка вернуться вверх
- анонимные комментарии к постам
- скачивание файлов по постоянной ссылке

### Админ панель

- вход по логину и паролю
- создание, редактирование и удаление постов и страниц
- статусы поста: черновик, доступен только по ссылке, опубликован
- предпросмотр поста в редакторе
- редактирование пунктов хедера и футера
- загрузка файлов (фото, видео, любые файлы) и вставка их в посты
- очередь комментариев на модерацию: одобрить или отклонить
- статистика обращений к страницам

Контракт API описан в [API.md](API.md).

## Технологии

- frontend: SvelteKit с SSR (`adapter-node`), TypeScript
- backend: Go, REST API
- база данных: PostgreSQL
- файлы: S3-совместимое хранилище [Garage](https://garagehq.deuxfleurs.fr/)
  внутри кластера
- деплой: k3s на своем сервере, обычные YAML манифесты в `deploy/k8s/`
- входящий трафик: Traefik (встроен в k3s), TLS через cert-manager
  и Let's Encrypt
- образы: GitHub Container Registry (ghcr.io)
- CI/CD: GitHub Actions

## Архитектура

- SvelteKit на сервере запрашивает данные у Go API по внутреннему
  адресу Service и отдает готовый HTML
- публичная часть и админка живут в одном приложении SvelteKit,
  админка по пути `/admin`
- S3 и PostgreSQL наружу не открыты, все обращения к файлам идут
  через backend

## Kubernetes

Кластер k3s из одного узла на своем сервере.

- namespace `nilptr`
- frontend и backend - Deployment без состояния, их можно
  масштабировать по числу реплик
- PostgreSQL и S3 - StatefulSet с PersistentVolumeClaim, тома выдает
  встроенный в k3s local-path provisioner (данные лежат на диске
  сервера)
- Ingress обслуживает встроенный Traefik, сертификаты выпускает
  cert-manager через Let's Encrypt
- пароли, секрет для `ip_hash` и ключи S3 хранятся в Secret,
  остальные настройки в ConfigMap
- миграции БД выполняются Job перед обновлением backend
- у frontend и backend есть liveness и readiness пробы
  (`/healthz`, `/readyz`)
- реальный IP клиента нужен для лимита комментариев:
  - у Service Traefik стоит `externalTrafficPolicy: Local`
    (настраивается через `HelmChartConfig` в k3s)
  - backend берет IP из `X-Forwarded-For`, доверяя только Traefik
- бэкап: CronJob делает `pg_dump` и копирует его вместе с файлами
  из S3 во внешнее хранилище, так как все данные лежат на одном диске

## CI/CD

Образы:

- `ghcr.io/ruslankarabalin/nilptr-frontend`
- `ghcr.io/ruslankarabalin/nilptr-backend`
- тег образа - короткий SHA коммита
- если пакеты в ghcr приватные, в кластере нужен `imagePullSecret`
  с токеном `read:packages`

Workflow GitHub Actions:

- на pull request: линтеры, тесты, проверка сборки frontend и backend
- на push в `main`:
  1. линтеры и тесты
  2. сборка образов и публикация в ghcr
  3. удаление Job миграций прошлого деплоя (Job нельзя изменить)
  4. применение Job миграций и ожидание ее завершения
     (`kubectl wait --for=condition=complete`)
  5. применение остальных манифестов из `deploy/k8s/`
  6. ожидание `kubectl rollout status` для frontend и backend

Тег подставляется в манифест перед применением:
`envsubst < manifest.yaml | kubectl apply -f -`.

В манифестах образы указаны с переменной, например
`ghcr.io/ruslankarabalin/nilptr-backend:${IMAGE_TAG}`.

Доступ к кластеру из GitHub Actions:

- отдельный ServiceAccount с правами только на namespace `nilptr`
- его kubeconfig хранится в секрете репозитория
- API k3s (порт 6443) должен быть доступен из GitHub Actions

## Решения по функциям

### Посты и формат

- текст поста хранится в БД в markdown
- markdown превращается в HTML на сервере SvelteKit: remark, remark-math,
  rehype-katex, формулы рендерятся через KaTeX
- тот же код используется для предпросмотра в админке
- итоговый HTML проходит санитайзер
- вставки файлов оформляются директивами markdown со ссылкой на id файла:
  - `::image{id=...}` - картинка
  - `::video{id=...}` - видео
  - `::file{id=...}` - плашка скачивания файла

### Статусы постов

- `draft` - виден только в админке
- `unlisted` - не показывается в ленте, доступен по ссылке с
  заданным путём `/posts/{name}`, страница отдается с
  `noindex`
- `published` - виден всем

### Хедер и футер

- пункты хранятся в БД: подпись, ссылка, расположение, порядок
- ссылка ведет либо на внутреннюю страницу, либо на внешний URL

### Файлы

- загрузка из админки идет через backend, он сохраняет файл в S3
- постоянная ссылка вида `/files/{id}/{name}`, backend отдает файл из S3
- ссылка перестает работать только при удалении файла

### Комментарии

- один комментарий в календарные сутки с одного IP на весь сайт
- лимит считает любую отправку, включая отклоненные
- IP не хранится, хранится `ip_hash = sha256(ip + secret + дата)`
- уникальный индекс по `ip_hash` атомарно обеспечивает лимит
- защита от ботов: скрытое поле-ловушка
- все комментарии проходят премодерацию, публично видны только одобренные

### Статистика

- каждая страница публичной части после загрузки отправляет
  `POST /api/views` с путем страницы
- backend записывает в БД путь и время обращения
- страницы админки не считаются
- в админке: число обращений по страницам за выбранный период

### Аутентификация

- один администратор, логин и пароль
- пароль хранится в виде хэша

Токены:

- access токен - JWT со сроком жизни 15 минут, подпись HS256
  секретом из Secret
- refresh токен - случайная строка со сроком жизни 30 дней,
  в БД хранится только ее хэш
- оба токена лежат в cookie с `HttpOnly`, `Secure`, `SameSite=Strict`,
  cookie refresh токена имеет путь `/admin`, чтобы SvelteKit получал
  его на страницах админки
- SvelteKit на сервере передает cookie в Go API, при истекшем access
  токене сам вызывает refresh

Устройства и защита от кражи:

- каждый refresh токен привязан к устройству: user-agent, IP при
  выдаче, время выдачи и последнего использования
- при каждом refresh старый токен отзывается и выдается новый
  (ротация), новый наследует семейство старого
- если приходит уже отозванный токен, значит его украли: отзывается
  все семейство, и вход на этом устройстве требуется заново
- исключение: токен, замененный ротацией менее 10 секунд назад
  (одновременный refresh из двух вкладок), просто отклоняется
- если user-agent при refresh не совпадает с сохраненным, токен
  отклоняется
- в админке есть список устройств с возможностью завершить любой
  сеанс
- logout отзывает refresh токен текущего устройства
